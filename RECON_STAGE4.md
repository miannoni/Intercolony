# Stage 4 seam map — F05 receiving locations and F12 programmed caravans

## Scope and source findings — READ

F05 asks for marked vanilla storage destinations whose own filters remain authoritative, with any marked destination that accepts the arriving goods and has room eligible; it asks for vanilla storage/hauling logic and preservation of the current behavior when no destination is configured (`docs/PLAYTEST_BATCH_SOURCE_PLAN.md:178-198`). F12 asks for one-upcoming or recurring caravan configuration for selling and procurement agreements, with a programmed caravan waiting rather than knowingly leaving a partial order and reporting the available fraction (`docs/PLAYTEST_BATCH_SOURCE_PLAN.md:226-270`).

The older 1.0 plan explicitly lists “Receiving / Dispatch zones” as cut, so neither feature is an existing 1.0 seam waiting for a small switch (`docs/INTERCOLONY_1_0_IMPLEMENTATION_PLAN.md:124-133`).

## A. Where goods arrive today — READ

### Supplier-delivered purchase

1. The purchase UI chooses `Find.CurrentMap ?? Find.AnyPlayerHomeMap` and passes that map as `paymentMap` into `PurchaseOrderService.AcceptQuote` (`Source/Intercolony/UI/MainTabWindow_Intercolony.cs:5140-5196`). `AcceptQuote` passes the same map into `TryCreatePaidOrder` (`Source/Intercolony/Procurement/PurchaseOrderService.cs:97-116`), and `CreateOrder` stores it as `destinationMap` (`Source/Intercolony/Procurement/PurchaseOrderService.cs:148-197`). The order documents this field as both the destination colony and the map that paid (`Source/Intercolony/Procurement/PurchaseOrder.cs:62-67`); it is saved with `Scribe_References` (`Source/Intercolony/Procurement/PurchaseOrder.cs:134-156`).

2. The hourly world tick advances confirmed purchases, and the coarse refresh advances them too (`Source/Intercolony/Core/IntercolonyWorldComponent.cs:1626-1638`, `Source/Intercolony/Core/IntercolonyWorldComponent.cs:1741-1748`). `AdvanceOrders` calls `DeliverToColony` for supplier-delivered orders and otherwise changes the order to `ReadyForPickup` (`Source/Intercolony/Procurement/PurchaseOrderService.cs:364-398`).

3. `DeliverToColony` resolves the recorded map if it is still in `Find.Maps`, otherwise falls back to `Find.AnyPlayerHomeMap`; if there is no map it holds the order (`Source/Intercolony/Procurement/PurchaseOrderService.cs:401-446`). For ordinary goods it calls `SpawnGoods(order, map, DropCellFinder.TradeDropSpot(map))` (`Source/Intercolony/Procurement/PurchaseOrderService.cs:410-430`).

4. `MakeGoods` creates the promised def, stuff, quality, stack count, and minified form (`Source/Intercolony/Procurement/PurchaseOrderService.cs:869-906`). `SpawnGoods` then tries each created `Thing` at the single trade-drop center with `GenPlace.TryPlaceThing(..., ThingPlaceMode.Near)`; a failed placement destroys that `Thing`, and the method returns only the number placed (`Source/Intercolony/Procurement/PurchaseOrderService.cs:909-925`). `DeliverToColony` refunds only when zero were placed and otherwise calls `Complete` with the placed count (`Source/Intercolony/Procurement/PurchaseOrderService.cs:418-430`); `Complete` immediately sets the purchase status to `Completed` (`Source/Intercolony/Procurement/PurchaseOrderService.cs:655-706`). There is therefore no current “wait for receiving capacity” or full-order gate at this arrival seam.

5. `DropCellFinder.TradeDropSpot` prefers a valid spot near an orbital beacon or comms console and otherwise searches near colony buildings or a random valid spot; it does not enumerate storage destinations (`reference/decompiled/RimWorld/DropCellFinder.cs:26-75`). `GenPlace.TryPlaceThing` in `Near` mode searches radial cells around that center (`reference/decompiled/Verse/GenPlace.cs:27-71`, `reference/decompiled/Verse/GenPlace.cs:129-188`). Its candidate check enforces generic spawn/item-cell capacity and checks `IHaulDestination.Accepts` only when the candidate cell’s edifice implements that interface (`reference/decompiled/Verse/GenPlace.cs:214-248`). A stockpile is a `Zone_Stockpile`, not an edifice (`reference/decompiled/RimWorld/Zone_Stockpile.cs:7-8`), so this generic drop does not apply a stockpile zone’s filter. This is the F05 attachment point: `DeliverToColony`/`SpawnGoods`, before or inside the current `GenPlace` call (`Source/Intercolony/Procurement/PurchaseOrderService.cs:401-430`, `:909-925`).

6. Animal purchases intentionally leave this goods path: `DeliverToColony` branches to `DeliverAnimalsToColony` (`Source/Intercolony/Procurement/PurchaseOrderService.cs:410-415`), which generates animals and calls `AnimalPurchaseUtility.TryDeliverToColony` (`Source/Intercolony/Procurement/PurchaseOrderService.cs:532-550`). That utility finds an animal-safe map entry cell and spawns the pawn there (`Source/Intercolony/Procurement/AnimalPurchaseUtility.cs:147-185`); an animal is not a storage destination candidate.

### Player pickup and sales delivery

For a procurement pickup, `AdvanceOrders` only changes the order to `ReadyForPickup` (`Source/Intercolony/Procurement/PurchaseOrderService.cs:380-386`). A player-controlled caravan parked at the supplier receives a “Collect purchase” gizmo (`Source/Intercolony/Orders/CaravanDeliveryGizmos.cs:22-60`), whose action calls `PurchaseOrderService.CollectWithCaravan` (`Source/Intercolony/Orders/CaravanDeliveryGizmos.cs:64-78`). That method creates the goods and adds each `Thing` to a selected caravan pawn’s inventory (`Source/Intercolony/Procurement/PurchaseOrderService.cs:457-529`); it does not place goods on the player’s map.

For a selling delivery, the caravan arrival action resolves the order and calls `SalesOrderService.ConfirmAndDeliver` (`Source/Intercolony/Orders/CaravanArrivalAction_DeliverOrder.cs:73-95`). `ConfirmAndDeliver` reaches `Deliver`, which validates and removes matching goods from caravan inventories, then puts payment into caravan pawn inventories (`Source/Intercolony/Orders/SalesOrderService.cs:319-397`, `Source/Intercolony/Orders/SalesOrderService.cs:1311-1349`). That is an outgoing handoff, not an incoming storage placement.

## B. Vanilla acceptance, room, and haul indexing — READ

The real vanilla chain is:

- `StorageSettings` owns the `ThingFilter` and priority, persists both, and answers filter acceptance through `AllowedToAccept(Thing)` or `AllowedToAccept(ThingDef)`; the `Thing` overload also applies parent/fixed-storage settings (`reference/decompiled/RimWorld/StorageSettings.cs:6-21`, `:78-129`).
- `ThingFilter.Allows(Thing)` checks the actual thing’s def, minified inner thing, hit points, quality, and special filters; `Allows(ThingDef)` is only the def-level test (`reference/decompiled/Verse/ThingFilter.cs:874-916`).
- `IHaulDestination.Accepts(Thing)` is the destination-level acceptance call; the interface has no `Accepts(ThingDef)` and no generic room method (`reference/decompiled/RimWorld/IHaulDestination.cs:5-14`).
- `Building_Storage.Accepts(Thing)` delegates to `GetStoreSettings().AllowedToAccept`, and `Zone_Stockpile.Accepts(Thing)` delegates to its `StorageSettings` (`reference/decompiled/RimWorld/Building_Storage.cs:100-140`, `reference/decompiled/RimWorld/Zone_Stockpile.cs:111-132`).
- `SlotGroup` is the storage-cell abstraction: it exposes settings, held things, and cells, and registers or clears cells in the map’s haul manager when cells change (`reference/decompiled/RimWorld/SlotGroup.cs:6-16`, `:18-60`, `:83-100`).
- `HaulDestinationManager` owns the ordered `IHaulDestination` list, ordered `SlotGroup` list, and cell-to-slot-group grid; it sorts destinations/groups by storage priority and exposes `SlotGroupAt`/`SlotGroupParentAt` (`reference/decompiled/RimWorld/HaulDestinationManager.cs:6-32`, `:57-85`, `:136-166`).

The closest single vanilla answer to “does this specific storage cell accept this actual thing and have room?” is `StoreUtility.IsValidStorageFor(IntVec3, Map, Thing)`: it calls `NoStorageBlockersIn` and then `slotGroup.parent.Accepts(storable)` (`reference/decompiled/RimWorld/StoreUtility.cs:103-115`). `NoStorageBlockersIn` checks mergeable stack capacity, per-cell item limits, and blockers (`reference/decompiled/RimWorld/StoreUtility.cs:117-142`).

The vanilla destination selector is `StoreUtility.TryFindBestBetterStorageFor`, which considers the best slot-group cell and non-slot destination (`reference/decompiled/RimWorld/StoreUtility.cs:144-170`). Its slot-group search walks `HaulDestinationManager.AllGroupsListInPriorityOrder`, requires an enabled destination, applies `StorageSettings.AllowedToAccept`, and then calls `IsGoodStoreCell` (`reference/decompiled/RimWorld/StoreUtility.cs:173-240`). Its non-slot search walks `AllHaulDestinationsListInPriorityOrder`, calls `IHaulDestination.Accepts`, and for `IHaulEnroute` containers checks `GetSpaceRemainingWithEnroute` (`reference/decompiled/RimWorld/StoreUtility.cs:242-325`; `reference/decompiled/RimWorld/IHaulEnroute.cs:5-10`; `reference/decompiled/Verse.AI/EnrouteUtility.cs:6-12`).

There is no vanilla “receiving locations” subset. The vanilla logic knows acceptance, priority, cells, blockers, reservations, and reachability; F05 still needs a separate marker to restrict the candidates to the player’s chosen destinations (`reference/decompiled/RimWorld/HaulDestinationManager.cs:18-32`, `reference/decompiled/RimWorld/StoreUtility.cs:144-240`).

## C. Marking a storage as receiving — READ

The mod has one per-map program precedent, not a storage precedent. `ProduceLoopMapComponent` is a `MapComponent` with a list of records, and each record is looked up by an `IntVec3` cell (`Source/Intercolony/Production/ProduceLoopMapComponent.cs:7-17`, `:157-177`). Its enable/disable operations add or remove cell-keyed records (`Source/Intercolony/Production/ProduceLoopMapComponent.cs:213-245`), and its save path deep-saves the record list (`Source/Intercolony/Production/ProduceLoopMapComponent.cs:269-283`; `Source/Intercolony/Production/ProduceLoopRecord.cs:5-28`). The production gizmo is added by a Harmony postfix on `Thing.GetGizmos` and edits the map component (`Source/Intercolony/Production/ProduceGizmoPatch.cs:9-48`, `:50-97`).

There is no production `ThingComp` in the mod, and no existing receiving or per-zone state. The exact search `rg -n "class .*ThingComp|: *ThingComp\b|\bThingComp\b" Source/Intercolony --glob '*.cs'` returned no matches. The exact search `rg -n -i "ReceivingLocation|ReceivingLocations|DeliveryDestination|Intercolony.*Receiving|Receiving.*Intercolony|DispatchZone|ReceivingZone" Source/Intercolony` returned no matches. The only `ThingID` search hit was diagnostic pawn-id serialization in `Source/Intercolony/Debug/Bridge/IntercolonyDevBridgeHost.cs:593-615`, not receiving state.

Vanilla already gives the UI seam: `Building_Storage.GetGizmos` yields storage copy/paste and storage-group gizmos (`reference/decompiled/RimWorld/Building_Storage.cs:227-253`), while `Zone_Stockpile.GetGizmos` yields stockpile and storage copy/paste gizmos (`reference/decompiled/RimWorld/Zone_Stockpile.cs:75-86`). A receiving command would therefore need to join the building gizmo path for shelves/building storage and the zone gizmo path for stockpiles; the existing `Thing.GetGizmos` patch is a precedent for the building half, not for zones (`Source/Intercolony/Production/ProduceGizmoPatch.cs:12-48`).

What does not exist yet is the marker itself, its UI command, and the filtering of vanilla candidates by that marker. Vanilla storage filters remain the authority once a marked destination is considered (`reference/decompiled/RimWorld/StorageSettings.cs:97-129`; `reference/decompiled/RimWorld/StoreUtility.cs:103-142`).

## D. Map-scoped persistence for receiving destinations — READ

`ProduceLoopMapComponent` explicitly states that map-component state is saved in the map block and is independent of the world-level schema/migration ladder (`Source/Intercolony/Production/ProduceLoopMapComponent.cs:7-11`). Its `ExposeData` saves a deep record list without touching `IntercolonyWorldComponent` (`Source/Intercolony/Production/ProduceLoopMapComponent.cs:274-283`).

The world component is instead the authoritative owner of cross-map economic state, with schema version `57`, and its `ExposeData` deep-saves orders and contracts (`Source/Intercolony/Core/IntercolonyWorldComponent.cs:11-30`, `Source/Intercolony/Core/IntercolonyWorldComponent.cs:1161-1201`). Existing order records save their map references with `Scribe_References` (`Source/Intercolony/Orders/SalesOrder.cs:278-318`, `Source/Intercolony/Procurement/PurchaseOrder.cs:134-156`).

The storage marker is map-local, so a map component is the right home for it: the marker describes which storage on this map may receive, not a world-level contract or economic entity (`Source/Intercolony/Production/ProduceLoopMapComponent.cs:7-11`; `docs/PLAYTEST_BATCH_SOURCE_PLAN.md:184-194`). This is a conclusion about ownership, and it deliberately differs from the world component’s rule for authoritative economic state (`Source/Intercolony/Core/IntercolonyWorldComponent.cs:11-22`).

The persistence record must distinguish the two vanilla object kinds:

- A `Zone` has a persisted integer `ID`, is saved by `ZoneManager` as a deep zone list, and exposes the load identity `Zone_` plus that ID (`reference/decompiled/Verse/Zone.cs:10-20`, `:187-208`, `:404-420`; `reference/decompiled/Verse/ZoneManager.cs:5-37`).
- A storage building is a `Thing` (`reference/decompiled/RimWorld/Building_Storage.cs:8-10`). `Thing` has a `thingIDNumber`, exposes the load identity `Thing_` plus `ThingID`, and saves the ID/map/position through `ExposeData` (`reference/decompiled/Verse/Thing.cs:15-27`, `:777-801`, `:1219-1244`).

Therefore a receiving record would need a map-owned saved reference or stable key for a `Zone` and a separate saved reference or stable key for a `Building_Storage`; it must resolve each against the loaded map and prune a deleted zone or destroyed/despawned building. A single cell key is insufficient for a zone/building marker because a zone owns many cells and a building’s occupied cells can change (`reference/decompiled/Verse/Zone.cs:20-20`, `reference/decompiled/RimWorld/Building_Storage.cs:83-97`). No such record or post-load cleanup exists today (`Source/Intercolony/Production/ProduceLoopMapComponent.cs:13-17`, `:269-283`; exact receiving-state search in section C).

## E. Caravan formation and dispatch — READ

### Current selling-delivery entry points

- The mod appends selling arrival options to the vanilla settlement float menu (`Source/Intercolony/Compatibility/HarmonyPatches.cs:25-61`). `CaravanArrivalAction_DeliverOrder.GetFloatMenuOptions` creates one arrival action per open order (`Source/Intercolony/Orders/CaravanArrivalAction_DeliverOrder.cs:137-168`); `StillValid` and `CanDeliver` re-check the destination, order, hostility, and carried quantity (`Source/Intercolony/Orders/CaravanArrivalAction_DeliverOrder.cs:57-71`, `:104-135`); and `Arrived` calls `ConfirmAndDeliver` (`Source/Intercolony/Orders/CaravanArrivalAction_DeliverOrder.cs:73-95`).
- A parked caravan is handled separately by the `Caravan.GetGizmos` postfix (`Source/Intercolony/Compatibility/HarmonyPatches.cs:64-96`). `CaravanDeliveryGizmos.GetGizmos` finds open sales orders at the visited settlement, and `BuildCommand` calls `ConfirmAndDeliver` (`Source/Intercolony/Orders/CaravanDeliveryGizmos.cs:22-60`, `:80-123`).
- Recurring sales cycles are raised by `ContractService.AdvanceContracts` (`Source/Intercolony/Contracts/ContractService.cs:1195-1273`). `RaiseCycleOrder` creates a `SalesOrder`, records its `activeOrderId`, and sends a notice; it does not form a caravan (`Source/Intercolony/Contracts/ContractService.cs:1652-1711`).

### Current procurement-pickup entry points

- The parked-caravan gizmo enumerates ready purchase orders and calls `BuildCollectCommand` (`Source/Intercolony/Orders/CaravanDeliveryGizmos.cs:51-78`). `CollectWithCaravan` adds goods to existing caravan pawn inventories and can stop on carrying capacity (`Source/Intercolony/Procurement/PurchaseOrderService.cs:457-529`). Animal pickup similarly calls `TryDeliverToCaravan`, which adds the generated pawn to the existing caravan (`Source/Intercolony/Procurement/PurchaseOrderService.cs:591-652`, `Source/Intercolony/Procurement/AnimalPurchaseUtility.cs:194-239`).
- Recurring procurement cycles are entered by the world refresh (`Source/Intercolony/Core/IntercolonyWorldComponent.cs:1741-1748`), advanced by `ProcurementContractService.AdvanceCycles` (`Source/Intercolony/Procurement/ProcurementContractService.cs:886-1029`), and created by `TryCreateCycleOrder`, which calls `PurchaseOrderService.TryCreatePaidOrder` with the contract’s fulfillment mode (`Source/Intercolony/Procurement/ProcurementContractService.cs:1058-1112`). None of these methods form or route a caravan.

The mod does not choose a caravan’s pawns or animals today. Its only caravan-forming patch adds eligible Intercolony employees to vanilla’s `AllSendablePawns` result; it does not select them, build transferables, or send a caravan (`Source/Intercolony/Compatibility/HarmonyPatches.cs:99-162`). The exact search `rg -n "CaravanMaker|new Caravan|StartFormingCaravan|FormAndCreateCaravan|ExitMapAndCreateCaravan|CaravanUtility\.Form|FormCaravan" Source/Intercolony --glob '*.cs'` found no mod formation call; its only hits were comments, `new CaravanArrivalAction_DeliverOrder` at `Source/Intercolony/Orders/CaravanArrivalAction_DeliverOrder.cs:159`, and a self-test reference to `Dialog_FormCaravan.AllSendablePawns` at `Source/Intercolony/Debug/IntercolonyLaborSelfTest.cs:181`.

Vanilla’s composition boundary is the caravan dialog. `Dialog_FormCaravan` owns a public `List<TransferableOneWay>` (`reference/decompiled/RimWorld/Dialog_FormCaravan.cs:13-42`), fills it from sendable pawns and reachable colony items (`reference/decompiled/RimWorld/Dialog_FormCaravan.cs:612-619`, `:1019-1040`), extracts the chosen pawns, and calls `CaravanFormingUtility.StartFormingCaravan` (`reference/decompiled/RimWorld/Dialog_FormCaravan.cs:650-686`). `AllSendablePawns` applies the eligibility rules, and `AllReachableColonyItems` supplies loadable items (`reference/decompiled/RimWorld.Planet/CaravanFormingUtility.cs:236-277`). `StartFormingCaravan` creates the forming-caravan lord from the selected pawns and transferables (`reference/decompiled/RimWorld.Planet/CaravanFormingUtility.cs:30-67`); the lord later calls `FormAndCreateCaravan` (`reference/decompiled/RimWorld/LordJob_FormAndSendCaravan.cs:302-306`), which reaches `CaravanMaker.MakeCaravan` (`reference/decompiled/RimWorld.Planet/CaravanExitMapUtility.cs:21-55`, `reference/decompiled/RimWorld.Planet/CaravanMaker.cs:6-52`).

A caravan is a world object with a `ThingOwner<Pawn>` plus trackers (`reference/decompiled/RimWorld.Planet/Caravan.cs:10-39`). Animals are pawns in that same pawn owner; adding a non-pawn item goes through caravan inventory (`reference/decompiled/RimWorld.Planet/Caravan.cs:466-523`). The current agreement records contain fulfillment mode, auto-ready, and active-order IDs, but no pawn/animal selection (`Source/Intercolony/Contracts/RecurringContract.cs:130-141`, `:264-299`; `Source/Intercolony/Procurement/ProcurementContract.cs:165-176`, `:247-257`, `:483-518`).

What does not exist yet for F12 is the persisted program, the configured pawn/animal set, invalid-program handling, a formation/dispatch scheduler, and the attachment of a programmed arrival action to a newly formed caravan (`Source/Intercolony/Orders/CaravanArrivalAction_DeliverOrder.cs:32-36`, `Source/Intercolony/Contracts/RecurringContract.cs:130-141`, `Source/Intercolony/Procurement/ProcurementContract.cs:165-176`).

## F. Full-order availability and the partial-order seam — READ

The existing Mark Ready check is buyer-pickup-only: `SalesOrder.CanMarkReady` requires `status == Accepted` and `fulfillment == BuyerPickup` (`Source/Intercolony/Orders/SalesOrder.cs:181-206`). `MarkReadyForPickup` calls `CanMarkReadyNow` before changing the status to `AwaitingCollection` (`Source/Intercolony/Orders/SalesOrderService.cs:714-766`).

`CanMarkReadyNow` calls `OrderValidator.ValidateColony` (`Source/Intercolony/Orders/SalesOrderService.cs:837-842`). `ValidateColony` scans stored colony candidates, records uncapped `totalPhysicalMatchingQuantity`, caps `matchedQuantity` to the remaining obligation, and records `missingQuantity` (`Source/Intercolony/Orders/OrderValidation.cs:411-483`). `IsAvailableColonyStock` requires `Thing.IsInAnyStorage` (`Source/Intercolony/Orders/OrderValidation.cs:562-575`), so the existing check is storage-scoped but not receiving-location-scoped.

For ordinary goods, `CanMarkReadyNow` computes `available` as physical matching quantity minus other commitments, compares it to `order.RemainingQuantity`, and produces a reason containing both available and required counts (`Source/Intercolony/Orders/SalesOrderService.cs:844-860`). For animals it uses a separate available-animal count and designated-animal check (`Source/Intercolony/Orders/SalesOrderService.cs:845-877`). The public `CanMarkReadyNow` surface currently returns only `bool` plus a reason (`Source/Intercolony/Orders/SalesOrderService.cs:789-797`), but the internal calculation already has the numbers needed for a `5/10` report (`Source/Intercolony/Orders/SalesOrderService.cs:851-859`).

This check is not currently a programmed-caravan gate. Auto-ready only processes contracts whose order passes `CanMarkReady`, then calls `MarkReadyForPickup` (`Source/Intercolony/Contracts/ContractService.cs:1275-1321`); the long-term suite explicitly asserts that a seller-delivery cycle is never auto-readied (`Source/Intercolony/Debug/IntercolonyLongTermSelfTest.cs:619-630`).

The current handoff methods also permit partial operations: seller `Deliver` is documented and implemented as pro-rata partial delivery (`Source/Intercolony/Orders/SalesOrderService.cs:319-397`), and procurement `CollectWithCaravan` leaves the purchase open after a partial carrying-capacity handoff (`Source/Intercolony/Procurement/PurchaseOrderService.cs:489-527`). F12 therefore needs a pre-formation/full-order gate; reusing the current handoff call alone would not satisfy “must not leave with a knowingly partial order” (`docs/PLAYTEST_BATCH_SOURCE_PLAN.md:241-253`).

## Conclusions and proposed Stage 4 cut — CONCLUDE

### F05

Yes, F05 can reuse vanilla storage logic as the finding hopes. The settling citation is `StoreUtility.IsValidStorageFor`: it combines room/blocker checking with the destination’s `Accepts` call (`reference/decompiled/RimWorld/StoreUtility.cs:103-142`); the normal selector already walks priority-ordered slot groups and applies `AllowedToAccept` plus `IsGoodStoreCell` (`reference/decompiled/RimWorld/StoreUtility.cs:173-240`). `Building_Storage` and `Zone_Stockpile` both route `Accepts` to their existing storage settings (`reference/decompiled/RimWorld/Building_Storage.cs:100-135`, `reference/decompiled/RimWorld/Zone_Stockpile.cs:116-132`).

The smallest F05 seam is therefore: add a building/zone marker and map-scoped persistence, filter the vanilla candidate set to marked destinations, then use the existing acceptance/capacity path for the actual generated `Thing` at the `DeliverToColony`/`SpawnGoods` boundary (`Source/Intercolony/Procurement/PurchaseOrderService.cs:401-430`, `:909-925`; `reference/decompiled/RimWorld/StoreUtility.cs:103-240`). With no markers, retain the existing trade-drop `GenPlace` call so the F05 fallback is exactly the current behavior (`docs/PLAYTEST_BATCH_SOURCE_PLAN.md:188-194`; `Source/Intercolony/Procurement/PurchaseOrderService.cs:418-430`).

### F12

F12 is not one safe slice: it crosses agreement persistence, pawn/animal identity, stock availability, vanilla transferables, live caravan formation, world routing, arrival actions, and recurring-cycle policy (`docs/PLAYTEST_BATCH_SOURCE_PLAN.md:228-266`; `reference/decompiled/RimWorld/Dialog_FormCaravan.cs:612-686`; `Source/Intercolony/Contracts/ContractService.cs:1199-1321`; `Source/Intercolony/Procurement/ProcurementContractService.cs:886-1112`).

The smallest useful vertical slice is one upcoming, goods-only seller-delivery order on one map: persist a selected pawn set, show the existing availability result as `available/required`, wait while it is short, and only then form a vanilla caravan and attach the existing `CaravanArrivalAction_DeliverOrder`. Recurring cycles, procurement pickup, animals, multi-map routing, and renewal should follow as separate slices (`docs/PLAYTEST_BATCH_SOURCE_PLAN.md:234-251`; `Source/Intercolony/Orders/CaravanArrivalAction_DeliverOrder.cs:141-168`; `reference/decompiled/RimWorld.Planet/CaravanFormingUtility.cs:35-67`).

The first non-caravan unit can be even smaller: extract the Mark Ready quantity calculation into a structured availability result and add the `5/10` waiting/notification behavior. It is useful and directly testable, but it is not a complete F12 until the vanilla formation boundary is exercised (`Source/Intercolony/Orders/SalesOrderService.cs:794-860`; `docs/PLAYTEST_BATCH_SOURCE_PLAN.md:243-260`).
